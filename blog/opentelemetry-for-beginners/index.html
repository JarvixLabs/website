OpenTelemetry for Beginners: Metrics, Logs and Traces in One Pipeline

By Jarvix Engineering · 13 October 2026 · 4 min read

Tools coveredOpenTelemetryPrometheusJaegerGrafanaKubernetesDatadog
TopicsObservabilityOpenTelemetry

If you have looked into observability recently, you have almost certainly come across OpenTelemetry (often shortened to OTel). It has become the industry standard for collecting telemetry from applications and infrastructure, and it is supported by every major observability vendor. This guide explains what it is, how the pieces fit together, and how to get a first pipeline running.

What problem does OpenTelemetry solve?

Before OpenTelemetry, each monitoring vendor shipped its own agents and libraries. Instrumenting your code for one vendor tied you to it, and switching meant re-instrumenting everything. OpenTelemetry provides a single, vendor-neutral set of APIs, SDKs and tools to generate, collect and export telemetry. You instrument once, then send the data wherever you like: Prometheus, Grafana, Jaeger, Elastic, Datadog, New Relic and many more.

OpenTelemetry is an open-source project under the Cloud Native Computing Foundation (CNCF), formed from the merger of OpenTracing and OpenCensus.

The three main signals

SignalWhat it tells youExample
MetricsNumeric measurements over time; cheap to store and great for alertingRequests per second, error rate, p95 latency, CPU usage
TracesThe path of a single request across services, broken into timed spansA checkout request that calls cart, payment and inventory services
LogsTimestamped records of discrete events, with detail"Payment declined for order 123: insufficient funds"

The real power comes from correlation. When logs carry the same trace ID as the trace, you can jump from a slow request straight to the exact log lines it produced. OpenTelemetry adds this context for you.

The building blocks

  • API and SDK: libraries for each language (Java, Go, Python, .NET, Node.js and others) that create spans, metrics and logs inside your application.
  • Instrumentation libraries: ready-made instrumentation for popular frameworks, HTTP clients and databases. Auto-instrumentation agents can add this without code changes in several languages.
  • OTLP: the OpenTelemetry Protocol, the standard wire format for sending telemetry.
  • The Collector: a standalone service that receives, processes and exports telemetry. This is the heart of most production setups.

Why you want the Collector

Applications can send data straight to a backend, but routing everything through the Collector gives you:

  • Decoupling: change backends by editing Collector config, not application code.
  • Processing: batching, retries, filtering noisy data, adding resource attributes such as environment and cluster, and removing sensitive fields.
  • Sampling: keep all error traces but only a fraction of successful ones, to control cost.
  • Fan-out: send the same data to more than one destination, which is useful during vendor migrations.

A Collector pipeline has three stages: receivers (data in), processors (transform) and exporters (data out).

A minimal Collector configuration

This example receives OTLP data from applications and sends traces to Jaeger (or Tempo), metrics to Prometheus and logs to Loki:

receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  memory_limiter:
    check_interval: 1s
    limit_percentage: 80
  batch: {}
  resource:
    attributes:
      - key: deployment.environment
        value: production
        action: upsert

exporters:
  otlp/traces:
    endpoint: tempo:4317
    tls:
      insecure: true
  prometheus:
    endpoint: 0.0.0.0:8889
  otlphttp/logs:
    endpoint: http://loki:3100/otlp

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, resource, batch]
      exporters: [otlp/traces]
    metrics:
      receivers: [otlp]
      processors: [memory_limiter, resource, batch]
      exporters: [prometheus]
    logs:
      receivers: [otlp]
      processors: [memory_limiter, resource, batch]
      exporters: [otlphttp/logs]

Instrumenting an application

The fastest start is auto-instrumentation. For a Python service, for example:

pip install opentelemetry-distro opentelemetry-exporter-otlp
opentelemetry-bootstrap -a install

export OTEL_SERVICE_NAME=checkout
export OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318
opentelemetry-instrument python app.py

Your HTTP endpoints, outgoing requests and database calls now produce traces and metrics without any code changes. Add manual spans later for important business operations, such as "calculate price" or "reserve stock".

On Kubernetes, the OpenTelemetry Operator can inject auto-instrumentation into pods through an annotation, and manage Collectors for you.

Best practices from day one

  • Name services consistently with service.name and set deployment.environment. Good resource attributes make every query easier.
  • Follow semantic conventions for attribute names (for example http.request.method), so dashboards and tools work out of the box.
  • Watch cardinality. Never put user IDs, request IDs or full URLs into metric labels. They belong in traces and logs.
  • Sample deliberately. Tail-based sampling in the Collector lets you keep slow and failed requests while dropping routine ones.
  • Scrub sensitive data in the Collector before it leaves your network.

A sensible adoption path

  1. Deploy a Collector and send its output to your existing tools.
  2. Enable auto-instrumentation on one or two critical services.
  3. Connect logs to traces through trace IDs.
  4. Build dashboards and SLOs on the new signals, then roll out service by service.

OpenTelemetry has a learning curve, but it pays back quickly: one standard way to instrument everything, and the freedom to choose and change your observability backend without rewriting code.
