Terraform Module Structure for Multi-Environment Setups

By Jarvix Engineering · 15 September 2026 · 5 min read

Tools coveredTerraformGitHub Actions
TopicsTerraformInfrastructure as CodeDevOps

Terraform is easy to start with and surprisingly hard to scale. A single main.tf works for a proof of concept, but once you have dev, staging and production, several teams and a few hundred resources, structure becomes the difference between confident changes and nervous ones. This guide covers a layout that works well for most teams, and the reasoning behind it.

Goals of a good structure

  • Environments stay consistent. Staging should look like production, with differences that are explicit and small.
  • Blast radius stays small. A mistake in one component or environment should not be able to break everything else.
  • Code is reused, not copied. Common patterns live in modules, not in copy-pasted blocks.
  • Changes are reviewable. A pull request should make it obvious what will change and where.

Two kinds of Terraform code

The most useful mental model is to separate modules from live configurations:

  • Modules are reusable building blocks, such as a VPC, an EKS cluster or a Postgres database. They take inputs, create resources and return outputs. They never contain environment-specific values.
  • Live configurations (sometimes called stacks or root modules) call modules with concrete values for a specific environment and region. Each one has its own state.

A recommended repository layout

infrastructure/
├── modules/
│   ├── network/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   ├── outputs.tf
│   │   ├── versions.tf
│   │   └── README.md
│   ├── eks-cluster/
│   └── postgres/
└── live/
    ├── dev/
    │   ├── network/
    │   │   ├── main.tf        # calls ../../../modules/network
    │   │   ├── backend.tf
    │   │   └── terraform.tfvars
    │   ├── eks/
    │   └── postgres/
    ├── staging/
    │   └── ...same components...
    └── prod/
        └── ...same components...

Each folder under live/<env>/ is a separate root module with its own state file. Splitting by component (network, cluster, database) as well as by environment keeps plans fast and limits the blast radius of each apply.

Module design rules

1. One clear responsibility per module

A module should do one thing well: "a production-ready Postgres instance with backups, monitoring and parameter group", not "everything for service X". Large "kitchen sink" modules become hard to change safely.

2. A small, explicit interface

Expose only the inputs consumers genuinely need, with sensible defaults and validation:

variable "instance_class" {
  type        = string
  default     = "db.t4g.medium"
  description = "RDS instance class."
}

variable "environment" {
  type = string
  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "environment must be dev, staging or prod."
  }
}

3. Secure by default

Encryption at rest, private networking, deletion protection in production and least-privilege IAM should be the defaults, so that the easy path is also the safe path.

4. Pin provider and Terraform versions

terraform {
  required_version = ">= 1.6"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

5. Document inputs and outputs

A short README with an example call saves hours. Tools such as terraform-docs can generate the inputs and outputs tables automatically.

State: separate it deliberately

  • One state file per environment and component. Never share state between dev and prod.
  • Remote backend with locking, for example S3 with DynamoDB locking (or S3 native locking), Azure Storage or GCS.
  • Separate accounts or subscriptions per environment where possible. It's the strongest guardrail you can have.
  • Share values between stacks through outputs and terraform_remote_state or data sources, not by hard-coding IDs.

Versioning modules

Once more than one team consumes a module, version it. Either keep modules in a dedicated repository and tag releases, or publish them to a private registry. Live configurations then pin a version:

module "network" {
  source = "git::https://github.com/acme/terraform-modules.git//network?ref=v1.4.0"

  environment = "prod"
  cidr_block  = "10.20.0.0/16"
}

This lets you roll a module change through dev, then staging, then production, simply by bumping the version in each environment.

Workspaces, folders or Terragrunt?

ApproachGood forWatch out for
Folder per environment (above)Most teams; explicit and easy to reviewSome duplication of backend and provider blocks
Terraform workspacesIdentical, short-lived copies such as feature environmentsEasy to apply to the wrong workspace; differences between environments get hidden in conditionals
TerragruntMany environments and regions; removes backend boilerplateAn extra tool for the team to learn and maintain

Put it in a pipeline

Structure pays off fully when every change goes through CI/CD:

  1. On pull request: terraform fmt -check, validate, linting (tflint), security scanning (Checkov or Trivy) and plan, with the plan posted to the PR.
  2. On merge: apply to dev automatically, then promote to staging and production with approvals.
  3. Scheduled: a drift-detection plan that alerts when real infrastructure no longer matches code.

Checklist

  • Modules and live configurations are separated.
  • Each environment and component has its own remote state with locking.
  • Modules have small interfaces, validation, secure defaults and READMEs.
  • Provider and module versions are pinned.
  • Every change is planned and reviewed in CI before it is applied.

Get these foundations right early and your Terraform codebase will grow with your organisation instead of slowing it down.
