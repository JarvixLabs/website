On-Prem to Cloud Migration: The 7 Rs Explained

By Jarvix Engineering · 10 November 2026 · 5 min read

Moving from on-premises data centres to the cloud is rarely a single decision. A typical estate has hundreds of applications, and each one deserves its own migration strategy. The 7 Rs framework gives you a shared vocabulary for those decisions.

The idea started as Gartner's "5 Rs" in 2010. AWS later expanded it to six and then seven strategies, which is the version most teams use today. Azure and Google Cloud describe very similar options under slightly different names.

The 7 Rs at a glance

StrategyWhat it meansEffortCloud benefit
RetireSwitch the application offVery lowRemoves cost entirely
RetainKeep it on-premises for nowNoneNone, for now
Rehost"Lift and shift" servers as they areLowLow to medium
RelocateMove a whole platform, such as VMware, without changing itLowLow to medium
Replatform"Lift and reshape": small changes to use managed servicesMediumMedium to high
RepurchaseReplace with a SaaS productMediumHigh
RefactorRe-architect for cloud-native servicesHighHighest

Each strategy in more detail

1. Retire

Every discovery exercise finds applications that nobody uses, or that duplicate another system. Switching them off is the cheapest migration of all. It is common to find a meaningful share of an estate can be retired.

2. Retain

Some workloads should stay where they are for now: systems with strict data-residency rules, mainframes that are too risky to touch, hardware-dependent applications, or anything due to be replaced soon. Retaining is a valid decision as long as it is deliberate and revisited.

3. Rehost (lift and shift)

Move virtual or physical servers to cloud virtual machines with no code changes, often using tools such as AWS Application Migration Service or Azure Migrate. It is fast and low risk, and a good option when you need to exit a data centre by a deadline. The downside is that you bring along your existing operational overhead, and costs can rise if you don't rightsize afterwards.

4. Relocate

Move an entire platform without changing the workloads on it, for example running your VMware estate on VMware Cloud on AWS or Azure VMware Solution. It suits large virtualised estates that need to move quickly, and can be a stepping stone to further modernisation.

5. Replatform (lift and reshape)

Make targeted changes to benefit from managed services without rewriting the application. Typical examples are moving a self-managed database to Amazon RDS or Azure SQL, containerising an application onto a managed Kubernetes service, or moving file storage to object storage. Replatforming often gives the best balance of effort and benefit.

6. Repurchase

Replace an application with a SaaS product: a self-hosted CRM with Salesforce, an email server with Microsoft 365, or a self-hosted CI server with a hosted CI service. Data migration and user training are the main challenges.

7. Refactor (re-architect)

Redesign the application to be cloud native: breaking a monolith into services, using serverless functions, event-driven designs and managed data services. This brings the biggest gains in scalability, resilience and speed of delivery, but needs the most time and skill. Reserve it for applications that are strategically important and actively developed.

How to choose the right R

For each application, consider:

  • Business value: is it core to how you make money, or a commodity?
  • Pace of change: is it actively developed? Refactoring pays off for systems that change often.
  • Technical health: is it well understood, documented and tested?
  • Constraints: licensing, compliance, data residency, latency and hardware dependencies.
  • Timeline: a data-centre exit date favours rehosting first and modernising later.

A common pattern is to rehost or replatform first to meet a deadline, then refactor selectively once workloads are in the cloud and the team has built cloud skills.

Planning the migration in waves

  1. Discover: build an inventory of applications, servers, dependencies and owners. Dependency mapping is critical: applications that talk to each other heavily should usually move together.
  2. Assess and decide: assign one of the 7 Rs to each application and estimate cost and effort.
  3. Build the landing zone: accounts or subscriptions, networking, identity, security baselines, logging and cost controls, all as code.
  4. Pilot: migrate one or two low-risk applications end to end to prove the process and tooling.
  5. Migrate in waves: group applications by dependency and risk, with a rollback plan and a cut-over runbook for each wave.
  6. Optimise: rightsize, adopt autoscaling and savings plans or reserved capacity, and set up cost visibility.

Common pitfalls

  • Skipping discovery and finding hidden dependencies during cut-over.
  • Lifting and shifting everything and then being surprised that the cloud bill is higher than the data centre.
  • No landing zone, leading to inconsistent security and networking that is painful to fix later.
  • Underestimating data migration time and bandwidth for large databases.
  • Forgetting operations: monitoring, backup, incident response and cost management all change in the cloud.

Conclusion

The 7 Rs won't make your migration decisions for you, but they give everyone, from engineers to finance, a common language. Assess each application on its merits, move in well-planned waves, and treat the migration as the start of modernisation rather than the end.
