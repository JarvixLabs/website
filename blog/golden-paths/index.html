Golden Paths: How to Design Self-Service Templates Developers Actually Use

By Jarvix Engineering · 29 September 2026 · 4 min read

Tools coveredBackstageGitHubGitHub ActionsHelmGrafanaOpenTelemetry
TopicsPlatform EngineeringDeveloper Experience

A golden path is the opinionated, well-supported way to get a common job done in your organisation, such as creating a new microservice, adding a database or setting up a scheduled job. It is not the only way, but it is the easiest way, because the platform team has already solved the hard parts. Done well, golden paths are the single biggest lever a platform team has on developer productivity.

Golden path vs golden cage

The difference between a path developers love and one they work around comes down to a few principles:

Golden pathGolden cage
Optional, but clearly the easiest optionMandatory, enforced by policy
Sensible defaults with escape hatchesEverything locked down
Developers own the generated codeBlack box nobody understands
Evolves from developer feedbackDesigned once, then frozen

What a good golden path includes

For the classic "new service" path, the template should produce a working, deployable service in minutes, with:

  • A repository with a standard layout, a README and a working "hello world" endpoint.
  • A CI/CD pipeline already configured: build, unit tests, security and dependency scanning, container build and deployment to a dev environment.
  • Deployment configuration (for example a Helm chart or Kustomize overlay) with resource requests, health checks and autoscaling defaults.
  • Observability from the first commit: structured logging, metrics, tracing via OpenTelemetry, and a starter dashboard.
  • Secrets handled through your secrets manager, never in the repository.
  • Ownership metadata registered in the service catalogue.

A step-by-step approach

1. Pick the journey with the most pain

Interview a handful of developers and look at your ticket queue. The best first candidate is a journey that is frequent, slow and error-prone. "Create a new service and get it to production" is the usual winner.

2. Map the current journey

Write down every step a developer takes today, including waiting for approvals, copying config from another repo and asking colleagues for help. Time each step. This baseline is what you will measure improvement against.

3. Codify the best existing example

Don't design from scratch. Find the best-run service you already have and turn its setup into a template. It has already proven itself in production, and its owners become your first advocates.

4. Choose the delivery mechanism

  • Developer portal templates, such as Backstage Software Templates, give a form-based experience and register the result in the catalogue.
  • CLI scaffolding tools such as Cookiecutter or Copier suit teams who live in the terminal.
  • Template repositories on GitHub or GitLab are the simplest place to start.

Start with the simplest mechanism that works. You can always add a portal later.

5. Keep parameters few

Ask only for what genuinely varies: service name, owning team, language, and perhaps whether it needs a database. Every extra question is a decision you are pushing back onto the developer.

6. Plan for day two

Generating a service is the easy part. Decide how improvements reach services created months ago. Options include shared pipeline templates referenced by version, base container images that are rebuilt centrally, and automated pull requests (for example with Renovate) that update dependencies and configuration.

7. Measure and iterate

  • Time to first deployment of a new service.
  • Adoption: the share of new services created from the golden path.
  • Drift: how far existing services have moved from the current template.
  • Developer satisfaction, through short surveys after use.

Common pitfalls

  • Too many templates. Five well-maintained paths beat thirty stale ones.
  • No owner. Each golden path needs a named team responsible for keeping it current.
  • Hidden magic. If developers can't read and change what was generated, they will stop trusting it.
  • Ignoring feedback. When teams diverge from the path, find out why. It is usually a missing feature, not a discipline problem.

Where to go next

Once your first golden path is adopted, extend the same approach to the next most common journeys: adding a database, creating a scheduled job, or exposing a service publicly. Each new path removes a little more friction, and together they become the foundation of your internal developer platform.
