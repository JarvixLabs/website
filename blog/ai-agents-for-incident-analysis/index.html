Using AI Agents for Incident Analysis: Architecture and Guardrails

By Jarvix Engineering · 24 November 2026 · 4 min read

Tools coveredPrometheusGrafanaKubernetesGitHubArgo CDPagerDutySlack

When an incident starts, the first 15 to 30 minutes are often spent gathering context: which alerts fired, what changed recently, which dashboards look wrong, which logs show errors. It is repetitive work under pressure, and it is exactly the kind of work that AI agents, large language models that can call tools and reason over the results, are now good at.

This post outlines how to design an incident analysis agent that helps on-call engineers without creating new risks.

What an incident agent can do

  • Gather context automatically as soon as an alert fires: related alerts, recent deployments and config changes, error logs, trace samples and the relevant dashboards.
  • Correlate signals across metrics, logs, traces and change history to suggest likely causes, with the evidence behind each one.
  • Find similar past incidents and their resolutions from postmortems and tickets.
  • Suggest next steps from your runbooks, and run read-only diagnostic commands.
  • Keep the timeline and draft status updates and the post-incident review.

What it should not do, at least at first, is take production-changing actions on its own.

A reference architecture

The main components are:

  • Trigger: a webhook from your alerting system starts an investigation and creates or joins the incident channel.
  • The agent loop: the model decides which tool to call next, reads the result and continues until it has enough evidence or hits a step limit.
  • Tools: small, well-described functions such as query_metrics, search_logs, get_recent_deploys and get_pod_events. The Model Context Protocol (MCP) is a useful standard for exposing these tools to agents in a consistent way.
  • Knowledge retrieval: runbooks and past postmortems indexed for search, so the agent can ground its suggestions in your own history.
  • Output: a structured summary posted to the incident channel.

Designing good tools

The quality of an agent depends far more on its tools than on clever prompts.

  • Make tools narrow and well named. get_error_rate(service, window) works better than a generic "run any PromQL" tool.
  • Return summaries, not raw dumps. Ten thousand log lines will overwhelm the model. Return counts, top error messages and a few examples.
  • Include links to the dashboard or log query behind every result, so humans can verify quickly.
  • Start read-only. The first version should not be able to change anything.

Guardrails you need

RiskGuardrail
Agent takes a harmful actionRead-only credentials by default; any write action requires explicit human approval in the channel
Confident but wrong conclusionsRequire evidence and links for every claim; present hypotheses with confidence, not verdicts
Sensitive data sent to a modelRedact secrets and personal data in tool outputs; consider self-hosted or region-pinned models
Runaway loops and costStep limits, timeouts and token budgets per investigation
Prompt injection via logs or ticketsTreat tool output as untrusted data; never let it change the agent's permissions or instructions
No accountabilityLog every tool call, input and output for audit and later review

A good output format

Engineers under pressure need something they can scan in seconds:

Incident: Checkout error rate 6.2% (threshold 2%), started 14:02 UTC

Likely causes (ranked):
1. Deploy checkout v2.41.0 at 13:58 UTC (4 min before onset)
   Evidence: errors are all "NullPointerException in PriceCalculator",
   first seen in v2.41.0 pods only. [logs] [deploy]
2. Payment provider latency (lower confidence)
   Evidence: p95 latency up 20%, but no error increase. [dashboard]

Similar incident: INC-1042 (bad price config), resolved by rollback.
Suggested next step: roll back checkout to v2.40.3 (requires approval).

Rolling it out safely

  1. Shadow mode: run the agent on real incidents but post its findings privately. Compare them with what the humans found.
  2. Assistant mode: post summaries into incident channels as suggestions, clearly labelled as AI-generated.
  3. Approved actions: allow a small set of safe, reversible actions, such as a rollback or scaling up, behind a one-click human approval.
  4. Measure: track time to first useful hypothesis, time to mitigation, how often suggestions were right, and on-call feedback.

Where agents help most, and least

Agents are most valuable for frequent, pattern-based incidents: bad deployments, resource exhaustion, dependency failures and configuration mistakes. They are least reliable for novel failures with little telemetry, which is exactly where experienced engineers remain essential. The goal is not to replace on-call engineers but to hand them a well-organised starting point, so they spend their time on judgement rather than on copying links between tabs.

Getting started

Begin with good observability and clean change history, because an agent can only reason over the data it can reach. Then build a small set of read-only tools, run in shadow mode for a few weeks, and expand only when the results earn your team's trust.
