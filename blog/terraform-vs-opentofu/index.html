Terraform vs OpenTofu: Differences, Licensing and How to Choose

By Jarvix Engineering · 26 November 2026 · 5 min read

Tools coveredTerraformOpenTofuGitHub Actions

For almost a decade, "infrastructure as code" and "Terraform" were close to synonyms. That changed in 2023, when HashiCorp moved Terraform to a source-available licence and the community responded with OpenTofu, an open-source fork. Today both tools are actively developed, and many teams are asking which one they should standardise on. This guide explains the differences and how to decide.

A short history

  • August 2023: HashiCorp announced that future Terraform releases would move from the Mozilla Public License (MPL 2.0) to the Business Source License (BSL 1.1).
  • September 2023: a community fork, first called OpenTF and then renamed OpenTofu, was accepted into the Linux Foundation. It was forked from the last MPL-licensed Terraform release.
  • January 2024: OpenTofu 1.6.0, the first stable release, shipped.
  • Since then: both projects have added features independently. OpenTofu has also joined the Cloud Native Computing Foundation (CNCF), and IBM completed its acquisition of HashiCorp in 2025.

The licence difference

This is the root of the split, so it is worth understanding precisely.

  • OpenTofu is licensed under MPL 2.0, an open-source licence. You can use, modify and redistribute it, including in commercial products.
  • Terraform (version 1.6 and later) is licensed under BSL 1.1. It is free to use, but the licence restricts offering it as part of a product that competes with HashiCorp's own commercial offerings.

For most companies that simply use Terraform to manage their own infrastructure, the BSL does not restrict day-to-day use. It matters most to vendors building platforms or services on top of Terraform. If you are unsure how it applies to you, ask your legal team; this article is not legal advice.

Features that now differ

OpenTofu

  • State encryption: encrypt state and plan files on the client side, so secrets in state are protected even if your backend is compromised.
  • Early variable evaluation: use variables and locals in places Terraform does not allow, such as backend configuration and module sources.
  • Provider iteration: for_each on provider configurations, which simplifies multi-region and multi-account setups.
  • Excluding resources: an -exclude flag, the opposite of -target, for planning around a resource.

Terraform

  • HCP Terraform integration: remote runs, policy as code with Sentinel, private registry and a managed workflow from the same vendor.
  • Terraform Stacks: a way to manage many related configurations and deployments together, aimed at large estates.
  • Vendor support: commercial support contracts directly from HashiCorp.

Both tools continue to add features such as testing frameworks and ephemeral values, sometimes with different syntax. The longer the projects diverge, the more important it is to pick one and use its features deliberately.

How to choose

OpenTofu is usually the better fit if:

  • Open-source licensing and community governance are important to your organisation.
  • You build a product or internal platform that embeds infrastructure as code.
  • You want state encryption or the other OpenTofu-only features.
  • You use, or plan to use, a third-party automation platform rather than HCP Terraform.

Terraform is usually the better fit if:

  • You already rely on HCP Terraform or Terraform Enterprise, including Sentinel policies.
  • You want commercial support from a single vendor.
  • Your team depends on Terraform-only features such as Stacks.

If neither list clearly applies, either tool will serve you well. Consistency across your organisation matters more than the choice itself.

Migrating from Terraform to OpenTofu

For configurations written for Terraform 1.5 or earlier, migration is usually straightforward. For newer versions, check the OpenTofu migration guide for your exact release first.

  1. Back up your state and make sure there are no pending changes: terraform plan should show nothing to do.
  2. Install OpenTofu and pin the version in CI, just as you would for Terraform.
  3. Initialise in the same directory: 
    tofu init
tofu plan   # should report no changes
  4. Review any differences in the plan before applying anything.
  5. Update your pipelines to call tofu instead of terraform, starting with a non-production environment.
  6. Roll out gradually, one environment and one component at a time, as described in our guide to Terraform module structure.

Avoid running both tools against the same state at the same time. Once a state file has been written by one tool, keep using that tool for it.

Summary

Terraform and OpenTofu share the same roots, language and provider ecosystem, but they now differ in licence, governance and a growing set of features. Choose Terraform if you are invested in HashiCorp's commercial platform; choose OpenTofu if open-source licensing, community governance or its unique features matter to you. Whichever you pick, standardise on it, pin versions and run every change through a reviewed pipeline.
